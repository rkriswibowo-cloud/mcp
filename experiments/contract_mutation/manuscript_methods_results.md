# Supplementary Reconstruction Evidence — manuscript draft text

> **Status:** FULL SDK MUTATION PROBES COMPLETED. These are results of a new, small, controlled Python prototype using five simulated client IDs and ten deterministic local mock tools, not evidence that the original manuscript experiments were conducted or that the original figures were reproduced.

## Methods — operational definitions (English, manuscript-ready)

A follow-up reconstruction-based validation was conducted using two Python implementations: a direct architecture implemented through a reusable adapter registry and an MCP architecture using the official Python MCP SDK, a FastMCP server, a ClientSession client, and stdio transport. Five logical client identifiers and ten deterministic local mock tools were used without LLM inference or remote APIs. Integration modules were prespecified as `traditional.py` for the direct configuration (Q = 1) and `mcp_server.py` plus `mcp_client.py` for MCP (Q = 2); the common tool module was excluded from the averaging population for both architectures, but retained as an external local dependency.

Coupling was operationalized as the number of distinct local modules referenced by each integration module through Python imports or explicit source-file references, averaged across the Q integration modules. This measure is a Python module-level reconstruction of the manuscript's dependency-count definition; it is **not** the Java-specific CKJM/Chidamber–Kemerer CBO metric. Cohesion was operationalized with the manuscript's custom 0–10 score, Cohm_i = 10 R_i/P_i, where P_i = M_i(M_i−1)/2. Class methods and MCP-registered tool functions were included; a pair was coded as related if its two methods referenced at least one identical instance attribute or called the same locally imported tool helper. The decision and shared evidence for every pair were recorded separately. Means were unweighted across the prespecified modules. These source-structure analyses produce one observation per architecture and should not be treated as five statistical replicates.

For change-impact validation, five predefined external tool contracts (`mysql_query`, `postgres_query`, `github_issue`, `slack_message`, and `rest_get`) were changed separately in clean copies of the project to require `contract_version="v2"`. Following each external contract change, both architectures were run without adaptation; each was then repaired by modifying its integration boundary. The Ripple Effect measure was defined in advance as the number of integration source files actually edited to restore correct behavior for all five simulated clients and ten mock tools. The provider-side mock implementation was a common external change and was counted separately. Full verification requires successful requests using the official MCP SDK. The five change types constitute distinct scenarios, not randomized independent replications.

## Results — reconstruction only

Static module coupling was 1.00 (Traditional, Q = 1) and 1.50 (MCP, Q = 2). The custom 0–10 cohesion score was 10.00 (Traditional, Q = 1) and 8.33 (MCP, Q = 2). Across five prespecified tool-contract changes, the traditional and MCP implementations required on average 1.00 and 1.00 integration source-file edits, respectively. Each repair was validated with 50 successful mock-tool calls via the respective execution pathway.

These findings do not reproduce the original paper's reported CBO values (8.2 vs 3.4), Cohm values (3.4 vs 8.2), or Ripple Effect values (9 vs 2). The reconstruction uses a compact shared adapter in the direct implementation, which changes its coupling and change propagation behavior substantially. Moreover, the unbalanced numbers of included integration modules limit direct interpretation of the means. The follow-up should be reported separately as a sensitivity/reconstruction study, not substituted for missing historical observations or characterized as MCP-specific causal superiority.

## Suggested response to the reviewer

We agree that the original manuscript did not provide sufficient module-level records and measurement procedures to independently verify the modularity claims. We have therefore separated the original descriptive results from a new, auditable reconstruction based on the published operational formulas. The supplementary materials contain source-level coupling edges, evidence for every cohesion method pair, the number of analyzed modules, a predefined five-scenario contract-change protocol, unified source-code patches, and executable tests. We do not claim that the reconstructed results retroactively validate the original reported figures. The revised discussion describes the dependency on comparator design, metric operationalization, and the limited external validity of simulated LLM/tool components.
